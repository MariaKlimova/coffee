# Выполнение задачи Coffee

Следовать `AGENTS.md`; инструкции общие для Codex и Cursor. Нужен выбранный
пользователем тикет `COFFEE-N`, рабочий checkout и фактическая база изменений.
Если пользователь разрешил работу по всему бэклогу, координатор выбирает готовые
задачи по приоритетам и зависимостям. Иначе нужен явно выбранный тикет.
Не переносить разрешения из соседних проектов.

## Подготовка и реализация

1. Проверить cwd, `git status --short`, branch/HEAD и существующие worktrees.
   Сохранить чужие правки. Использовать отдельную именованную ветку;
   при координации бэклога каждой задаче выделить implementation-агента и worktree
   по `AGENTS.md`. В одиночном режиме worktree нужен при занятом/грязном checkout
   или запросе изоляции. Не создавать параллельные серверы вместе с worktree.
2. По [coffee-jira](../coffee-jira/SKILL.md) прочитать полный актуальный тикет,
   важные комментарии/AC и зависимости. Изучить затронутые callers и тесты.
   Не начинать scope, заблокированный невыполненной обязательной зависимостью.
3. Кратко обозначить план и проверки. Уточнять существенные продуктовые неясности;
   рутинные решения принимать самостоятельно. Если пользователь явно потребовал
   утверждение плана, дождаться его; уже утверждённый план повторно не согласовывать.
4. Реализовать в согласованном scope по профильным rules/skills. Backend и frontend
   соблюдать как отдельные роли с общим API-контрактом. Не копировать secrets/.env
   из соседних checkout. Зависимости ставить по lockfile без случайных обновлений.
5. Запустить релевантные проверки по [окружениям QA](../coffee-qa/environments.md).
   Для UI выполнить затронутый сценарий в доступном настоящем браузере. Ограничения
   среды и неподтверждённые интеграции фиксировать отдельно от успешных unit-тестов.

## Независимые review и QA

По разрешению в `AGENTS.md` запустить отдельного reviewer с
[coffee-review](../coffee-review/SKILL.md). Передать тикет, checkout, base/HEAD,
полный dirty scope, план и проверяемые логи. Reviewer не меняет код. Исполнитель
исправляет blocking, повторяет затронутые проверки; reviewer проверяет исправления.
Полный отчёт передать по существующему контракту, не сжимая findings.

После закрытия blocking запустить отдельного QA Tester по
[контракту роли](../../../.cursor/agents/qa-tester.md) и
[coffee-qa](../coffee-qa/SKILL.md). QA читает AC самостоятельно, принимает ту же
ревизию, не исправляет продуктовый код и публикует в тикете `PASS`/`FAIL`/`BLOCKED`.
Reviewer и QA — разные исполнители; реализация не считается независимой приёмкой.
Перед browser-проверкой передавать владение единственным браузером/сервером,
дождаться cleanup предыдущего исполнителя.

При FAIL исправить дефекты в scope, повторить затронутые проверки/review и QA новой
ревизии. При BLOCKED указать конкретный блокер и выполненное покрытие. Если механизм
делегации недоступен, не выдавать самопроверку за независимый этап.

## Handoff

Для продуктовой задачи до merge предоставить локальный preview и короткий сценарий
просмотра, зафиксировать показанную ревизию и дождаться решения пользователя.
Пользовательский просмотр не заменяет независимые review и QA. Один preview-сервер
на все задачи; пока он занят просмотром, другие задачи не запускают свои серверы.

Дать результат, ветку/ревизию и dirty scope, итог review, QA-вердикт, подтверждённую
ссылку/comment ID Jira и ограничения. Если отчёт не опубликован, явно сказать это
и вернуть готовый текст. Для работы без тикета допустимы review/проверки, но полный
Jira workflow не завершён и публиковать в случайный тикет нельзя.

Push/merge/deploy, смена Jira-статуса и удаление worktree не входят автоматически
в этот цикл; выполнять их при соответствующем действующем разрешении пользователя.
