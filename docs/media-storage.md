# Постоянные изображения каталога

`ImageField` хранит ключ объекта в PostgreSQL. При `MEDIA_STORAGE=s3` Django
сохраняет файлы через `django-storages` в отдельном S3-совместимом бакете.
`collectstatic` продолжает работать с локальной статикой, независимо от media.
Контракт API не меняется: `image_url` и `images[].url` — абсолютные URL.

## Переменные backend

| Переменная | Значение |
|---|---|
| `MEDIA_STORAGE` | `filesystem` по умолчанию для разработки; `s3` для хостинга |
| `AWS_ACCESS_KEY_ID` | Обязательный server-side ключ для S3 |
| `AWS_SECRET_ACCESS_KEY` | Обязательный server-side секрет для S3 |
| `AWS_STORAGE_BUCKET_NAME` | Обязательное имя бакета |
| `AWS_S3_ENDPOINT_URL` | Endpoint провайдера с `https://`; пусто для AWS S3 |
| `AWS_S3_REGION_NAME` | Регион из настроек провайдера |
| `AWS_S3_ADDRESSING_STYLE` | `auto` по умолчанию, либо `path` / `virtual` |
| `AWS_S3_CUSTOM_DOMAIN` | Необязательный публичный CDN hostname без схемы, пути и завершающего `/` |
| `SERVE_MEDIA` | Только локальная раздача filesystem через Django; выключена при S3 |

Неполный S3-конфиг и неизвестный `MEDIA_STORAGE` останавливают запуск.
Секреты задаются только в backend environment, не в git и не в `VITE_*`.
Пример для локального запуска — `backend/.env.example`. `render.yaml` описывает
исторический Render backend: его обязательные S3 secrets нужно задать до деплоя.
Новый тестовый Vercel/Neon стенд настраивается отдельно; существующий production
и его данные автоматически не переносятся.

## Публичный доступ и бесплатный тестовый стенд

Для MVP выбран публичный доступ на чтение только к изображениям каталога.
Создание/изменение объектов требует backend credentials. Не хранить в этом бакете
заказы, контакты покупателей или приватные файлы. Django выдаёт URL без срока
действия, не отправляет S3 ACL и не перезаписывает объект при совпадении имени.

Публичный read-доступ включается средствами провайдера: bucket policy или
публичный CDN. Без `AWS_S3_CUSTOM_DOMAIN` публичный GET должен работать прямо
на S3 endpoint. С custom domain DNS/CDN должен указывать на этот же бакет.
Проверять GET из браузера без авторизации. Для обычного `<img>` отдельный CORS
не нужен; для `fetch` или canvas задать ограниченный CORS по origin фронтенда.

Для согласованного тестового стенда использовать только подтверждённый Free
план без карты/биллинга. Не создавать платные ресурсы и не переходить на платный
тариф ради media. Если бесплатный storage недоступен, остановить provisioning
и сообщить блокер. Проверять текущие лимиты провайдера перед созданием ресурса.

Neon Object Storage подходит через тот же S3-контракт: перенести endpoint из
`AWS_ENDPOINT_URL_S3` в `AWS_S3_ENDPOINT_URL`, регион из `AWS_REGION` в
`AWS_S3_REGION_NAME`, использовать `AWS_S3_ADDRESSING_STYLE=path`. Для backend
достаточен credential со scope `storage:write`, включающим чтение. Публичный
read-доступ к бакету включать в Neon Console/API, без `public-read` ACL.
Credentials привязаны к ветке Neon; использовать отдельный тестовый credential.
При ротации обновить secret в backend и явно отозвать старый credential;
на `expires_at` как механизм отзыва не полагаться.

Источники настроек:
[django-storages S3](https://django-storages.readthedocs.io/en/latest/backends/amazon-S3.html),
[Neon authentication](https://github.com/neondatabase/website/blob/main/content/docs/storage/authentication.md),
[Neon pricing](https://neon.com/pricing).

## Seed и существующие изображения

Обычный `backend/build.sh` устанавливает зависимости, собирает статику и запускает
миграции. Seed из build убран полностью. Для нового изолированного демокаталога
оператор явно запускает:

```bash
cd backend
python manage.py seed_catalog
```

Команда создаёт только отсутствующие товары по slug и их placeholders.
Повторный запуск не меняет существующие поля, категорию, доступность или галерею,
даже если изображение отсутствует в бакете. Существующий slug считается товаром
владельца. Команда не восстанавливает удалённые фотографии и не является миграцией.

Переход с filesystem не копирует старые файлы: ранее сохранённые ключи должны
быть перенесены в бакет отдельной согласованной операцией с резервной копией.
Не запускать seed для восстановления пользовательских изображений. Не удалять
старые файлы или записи до подтверждения переноса.

## Проверка реального стенда

1. На изолированном стенде загрузить PNG через Django admin, записать ключ объекта,
   URL из API и revision. Подтвердить наличие объекта в бакете и публичный GET.
2. Повторить deploy той же среды с теми же DB/bucket/env. Seed не запускать.
3. Подтвердить, что URL/ключ и поля изменённого тестового товара прежние, а GET
   возвращает прежнее изображение без авторизации.
4. Повторить ручной seed на тестовой БД и убедиться, что изменённый товар и его
   галерея сохранились. Зафиксировать evidence без credentials.

Unit-тесты с S3 Stubber проверяют storage-код и URL без обращения в облако;
они не доказывают публичную политику бакета или сохранение после реального deploy.
