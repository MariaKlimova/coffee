# Количественный остаток и резерв (COFFEE-62)

`Product.stock_quantity` — физическое количество упаковок/штук,
`reserved_quantity` — количество в активных резервах.
`available_quantity = stock_quantity - reserved_quantity`; `in_stock` вычисляется
как `available_quantity > 0`. Счётчики не могут быть отрицательными, резерв не
может превышать склад. Публикация `is_published` отдельна от наличия: скрытые
товары отсутствуют в публичном каталоге и не допускаются в корзину/checkout.
Корзина не резервирует товар; add, PATCH и merge проверяют итоговое количество.
Ошибка `400 / insufficient_stock` содержит `product_id`, `available_quantity`,
`requested_quantity`. При неудачном merge обе корзины сохраняются полностью.

## Checkout и оплата

Checkout блокирует корзину, затем все товары по UUID и атомарно проверяет каждую
позицию, создаёт снимки и строки резерва. Нехватка любой позиции отменяет всю
транзакцию. Резерв создаётся до обращения к провайдеру оплаты. В Order видны
`reservation_state`, `reservation_expires_at`, `stock_review_reason`.

Успешная подтверждённая провайдером оплата до конца резерва переводит его
`active → consumed`: склад и резерв уменьшаются на одинаковое количество.
Доступное число второй раз не уменьшается. Повторный webhook не списывает
остаток. Повторный запрос создания оплаты возвращает текущую pending-сессию;
после её отмены провайдером допускается новая попытка до окончания резерва.
Неуспех отдельной платёжной попытки сам по себе не отменяет заказ.

`cancel_unpaid_order(order_id=...)` — внутренний сервис отмены для COFFEE-61;
будущий staff API обязан отдельно проверить право на заказ/операцию. Он блокирует
Order и товары и освобождает активный резерв ровно раз. Оплаченный заказ отменять
этим сервисом нельзя. Никакие сервисы резерва не инициируют возврат или отмену
платежа у провайдера.

### Поздняя оплата и гонки

Все переходы оплаты, отмены и expiry используют общий порядок блокировок:
Order → Payment (если есть) → товары по UUID. Отмена и оплата сериализуются.
Если оплата побеждает, резерв списывается и отмена отклоняется. Если отмена или
истечение побеждает, подтверждённая оплата сохраняется как `Payment.succeeded`,
заказ получает явный `payment_review`, причина `payment_after_reservation_release`.

Даже если товары снова доступны, поздняя оплата **не захватывает их повторно**.
Новые резервы/продажи не затрагиваются. Требуется ручная проверка владельцем:
согласование наличия/дальнейших действий с покупателем; автоматического refund
нет. На витрине видны «Оплачен, уточняем наличие» и сообщение, что повторно
оплачивать не нужно. Платёжный retry для отменённого/review-заказа не предлагается.
Срок проверяется по времени обработки подтверждения сервером, не по payload
уведомления. UI управления этой ситуацией относится к COFFEE-61.

## Срок и действительно вызываемая очистка

`STOCK_RESERVATION_TTL_SECONDS` — положительное целое число секунд (по умолчанию
1800). Middleware перед запросами каталога, корзины, заказов и платежей снимает
до 100 просроченных неоплаченных резервов. Истечение переводит Order в
`cancelled`, резерв — в `released`. Это работает на serverless без отдельного
фонового процесса. В отсутствие трафика физическая очистка происходит при
следующем таком запросе. Большой backlog может временно уменьшать доступное
число, но не разрешает продажу сверх наличия.

Для явной полной очистки и дополнительного периодического запуска доступна
идемпотентная команда:

```bash
python manage.py expire_stock_reservations
```

Периодический cloud scheduler этой задачей не настраивается. Несколько cleanup
вызовов безопасны: они пропускают занятые Order (`skip_locked`) и блокируют общий
набор товаров по UUID. Оплата также сама проверяет deadline под блокировкой.

## Корректировка владельцем и аудит

Единая точка изменения физического количества для COFFEE-42:

```python
from apps.catalog.services import adjust_stock

product = adjust_stock(
    product_id=product_id, quantity=counted_quantity,
    actor=authenticated_staff, reason="Первоначальная инвентаризация",
)
```

Сервис повторно проверяет сохранённые `is_active/is_staff`, блокирует товар,
отклоняет отрицательное/дробное количество и количество ниже активного резерва.
Изменение и `StockAdjustment(actor, created_at, before_quantity, after_quantity,
reason)` атомарны. Аудит в техническом Django admin доступен только на чтение.
Сами счётчики в Django admin не редактируются; обычное сохранение Product не
перезаписывает загруженные ранее счётчики конкурентного checkout.

SPA управления количеством — COFFEE-42/45/47, дальнейшая UI-приёмка — COFFEE-46.
Гостевые и покупательские API не принимают изменения складских счётчиков.

## Безопасная миграция и первоначальное заполнение

До выкатки нужен согласованный план инвентаризации. Миграция сохраняет товары,
цены, историю и статусы старых заказов, но ставит **0 на складе и 0 в резерве**
каждому старому товару. Из boolean `in_stock` нельзя достоверно получить число.
Пока владелец не подтвердит реальные количества и они не внесены через
`adjust_stock`, такие товары нельзя купить. Деплой сам не мигрирует БД и не
заполняет остатки. `seed_catalog` создаёт новые demo-товары с нулём и никогда
не меняет существующие товары/вручную введённые количества. Повторные migrate
также сохраняют введённый остаток.

Старые заказы сохраняют `reservation_state=none`, без выдуманных резервов/списаний.
Исторические paid-заказы остаются paid. Старому pending-заказу нельзя создать
новую оплату: нужен новый checkout после сверки наличия. Если ранее созданный
провайдерский платёж всё же подтверждается, деньги сохраняются в Payment, Order
получает `payment_review / legacy_order_without_counted_stock`, склад не меняется.
До миграции нужно отдельно разобрать существующие pending/провайдерские сессии;
ничего автоматически не удаляется и деньги не возвращаются.

## Проверки

`tests/test_inventory.py` проверяет API-лимиты, merge, атомарность checkout,
списание/освобождение, позднюю оплату, audit/permissions и реальные конкурирующие
соединения PostgreSQL. `tests/test_inventory_migration.py` проверяет старые boolean
и pending/paid записи, отсутствие угадывания и сохранность ручных количеств при
повторной миграции. SQLite не заменяет эти проверки блокировок.
