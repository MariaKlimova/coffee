# Управление каталогом

Все `/api/manage/` endpoints требуют JWT активного staff. Анонимный запрос
получает 401, покупатель — 403. Полный контракт находится в `openapi.yaml`.

- `GET/POST /api/manage/products/`: список всех товаров и создание рабочего
  товара. Фильтры `category`, `search`, `is_published`, `origin`, `in_stock`,
  `price_min`, `price_max`, `ordering`; пагинация `page/page_size`.
- `GET/PATCH/DELETE /api/manage/products/{uuid}/`: просмотр, изменение и снятие
  публикации. DELETE сохраняет сам товар, галерею, остатки и связи с заказами.
- `POST /api/manage/products/{uuid}/images/`: загрузка одной фотографии.
- `PATCH/DELETE /api/manage/products/{uuid}/images/{image_id}/`: порядок,
  главное фото и удаление фотографии вместе с файлом.
- `GET /api/manage/catalog/`: сохранённое состояние demo и количества demo,
  рабочих и опубликованных рабочих товаров для подтверждения перехода в SPA.
- `POST /api/manage/catalog/disable-demo/`: необратимое в интерфейсе отключение
  demo. Повторный запрос возвращает прежние дату и состояние перехода.

При создании обязательны `name`, `category` (slug), `short_description`, `price`
и `stock_quantity`. Slug генерируется сервером и не меняется при переименовании.
`attributes` целиком заменяет объект характеристик и проверяется по итоговой
категории; смена категории не очищает характеристики молча.

`stock_quantity` — физический остаток, JSON integer от 0 до 2147483647.
`reserved_quantity` и `available_quantity` возвращаются только для чтения;
наличие вычисляется. Изменения количества идут через `adjust_stock` под блокировкой
строки товара и записывают actor, дату, старое/новое значение и причину.
`stock_change_reason` необязателен; стандартная причина — `Catalog stock adjustment`.
Уменьшение ниже текущего резерва возвращает `400 errors.stock_quantity` и откатывает
все поля этого PATCH. Покупатель не может записывать эти поля.

`origin=demo|owner` и `demo_source` назначает сервер. Миграция помечает только
18 UUID, действительно созданных импортом COFFEE-64
`catalog-data-20261101T123258089703Z`; совпадение названия/slug не является
доказательством происхождения. `seed_catalog` помечает только вновь созданные
записи и оставляет существующие данные, файлы и остатки нетронутыми.

Редактирование demo требует явного `save_as_owner=true` в PATCH. Без него API
возвращает ошибку этого поля, чтобы изменения не потерялись при отключении demo.
Этот же PATCH может содержать только `save_as_owner=true`: UUID, slug, исходный
`demo_source`, галерея и связи сохранятся, а origin станет `owner`.

Файлы-заглушки помечены `images[].is_mock`. `has_uploaded_images` считает только
реальные загруженные фотографии. После сохранения demo как рабочего его mock
файлы остаются видны в manage, но публичный ответ их не отдаёт. Frontend должен
использовать `origin` при выборе временной static mock-картинки; UUID сам по себе
не даёт права показывать mock у рабочего товара.

## Галерея товара

В manage `images[]` дополнительно содержит целочисленный `id` для операций
с фотографией. Публичный DTO по-прежнему содержит только `url`, `order`,
`is_main`, `is_mock`; адрес фотографии абсолютный. Текущую галерею читать
из `GET /api/manage/products/{uuid}/` и обновлять после каждой операции.

POST принимает `multipart/form-data` с единственным полем `image`: один JPEG,
PNG или WebP размером до **4 МиБ (4 194 304 байта)** включительно. Сервер
проверяет содержимое через Pillow, назначает UUID-имя и Content-Type по
подтверждённому формату; расширение и MIME браузера не считаются доказательством.
Лимит оставляет запас под multipart в пределах
[ограничения Vercel Functions 4,5 МБ](https://vercel.com/docs/functions/limitations#request-body-size).
Файл больше предела платформы может получить 413 до запуска Django.
Успешный ответ 201 — `{id, url, order, is_main, is_mock}`; `is_mock=false`.
Фото добавляется в конец, первая настоящая фотография автоматически становится
главной, заменяя mock-обложку при её наличии.

PATCH принимает JSON `{order?, is_main?}`. `order` — целочисленная позиция от 0
до `количество фото − 1`, остальные фотографии сдвигаются. `is_main=true`
заменяет главное фото. Нельзя снять признак с текущего главного через `false`:
сначала нужно выбрать другое главным, иначе вернётся `400 errors.is_main`.
Явно назначать mock главным нельзя (`400 errors.is_main`): он никогда не
показывается на витрине рабочего товара. Сохранённые mock не удаляются;
при наличии настоящих фотографий главное выбирается только среди настоящих.
Неизвестные и серверные поля не принимаются. Ответ 200 — изменённая фотография.
После успешной операции порядок плотный `0..n−1`, а при непустой галерее
есть ровно одно главное фото. Конкурентные операции API сериализуются блокировкой
строки товара; отсутствие главного у старой галереи исправляется при записи.

DELETE возвращает 204. При удалении главного выбирается первая оставшаяся
настоящая фотография по `order`, затем `id`. Если настоящих больше нет,
выбирается первый оставшийся mock для внутреннего инварианта, но публичная
галерея рабочего товара остаётся пустой. При удалении последней галерея пустая.
Неизвестная фотография, в том числе принадлежащая другому товару, даёт 404.
Повторный DELETE удалённой записи также даёт 404. Файл удаляется до записи:
если storage отклонил удаление, API возвращает 503 с
`code=image_storage_unavailable`, а запись и состояние галереи сохраняются
для повторной попытки. Ошибки провайдера не включаются в ответ.
PostgreSQL и object storage не образуют общей транзакции: сбой коммита БД
после успешного удаления файла требует сверки и восстановления оператором.
При ошибке сохранения строки после загрузки API пытается удалить новый файл;
неподтверждённый результат провайдера или ошибка cleanup также требуют сверки,
успешный ответ в этом случае не выдаётся.

Все изменения галереи доступны только рабочему товару `origin=owner`.
У demo вернётся `400 errors.save_as_owner`: сначала пользователь подтверждает
существующий product PATCH `save_as_owner=true`. Операция с фотографией сама
не меняет происхождение, публикацию или остаток товара. У неопубликованного
рабочего товара галерея редактируется штатно. Хранение файлов использует
выбранный backend [media storage](../media-storage.md), без отдельного локального
пути или credentials в SPA.

Отключение demo сохраняет все строки. Публичные list/detail/related и избранное
их скрывают; добавление в корзину и новый checkout их отклоняют. Уже созданные
заказы и резервы продолжают штатный жизненный цикл. Неопубликованность отличается
от скрытого demo через `hidden_reason`; при обеих причинах приоритет у
`unpublished`. Обычный seed, reload и повторное применение миграций не включают
demo обратно. Рабочие товары можно создавать до и после перехода.

Миграции и переключение production выполняются отдельно от сборки. Не откатывать
схему с удалением полей происхождения/состояния после перехода: это потеряет
сохранённое решение владельца. Для отката приложения сохранять совместимую схему.
